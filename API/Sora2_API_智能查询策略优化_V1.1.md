## 🎯 优化目标

在 V1.0 修复超时问题的基础上，进一步优化 Sora2 API 的查询策略，**减少不必要的 API 调用**，降低服务器负载和 API 配额消耗。

## 📊 数据支撑

### 实际 API 处理时间分析

根据 BizyAir API 返回的实际数据处理时间：

```json
{
  "cost_times": {
    "inference_cost_time": 84576,  // ≈ 84秒（1.4分钟）
    "total_cost_time": 86505,      // ≈ 86秒（1.43分钟）
    "real_gpu_cost_time": 82206    // ≈ 82秒（1.37分钟）
  }

```

**关键发现**：
- ✅ Sora2 任务平均需要 **1.4-1.5 分钟**完成
- ✅ 前 3 分钟是任务的主要处理期
- ✅ 3 分钟后任务有较高概率已完成
- ❌ V1.0 版本使用固定 10 秒间隔，前 3 分钟进行 18 次查询，浪费 API 调用

## ✨ 优化方案

### 智能延迟查询策略

根据任务处理时间的实际分布，采用**分阶段查询策略**：

#### 阶段划分

```python
# 前3分钟：低频查询期（每30秒）
early_phase_interval = 30秒
early_phase_duration = 180秒（3分钟）

# 3分钟后：高频查询期（每10秒）
late_phase_interval = 10秒
```

#### 代码实现

```python
def check_video_status(self, request_id):
    """查询BizyAir任务状态 - 智能延迟查询策略"""
    if self.video_mode in ["sora_t2v", "sora_i2v"]:
        max_attempts = 360
        early_phase_interval = 30  # 前3分钟每30秒查询一次
        late_phase_interval = 10   # 3分钟后每10秒查询一次
        early_phase_duration = 180  # 前期阶段持续3分钟
    else:
        # 其他模式保持原有策略
        max_attempts = 180
        check_interval = 10

    elapsed_time_total = 0

    for attempt in range(max_attempts):
        # 根据累计时间确定当前阶段和查询间隔
        if self.video_mode in ["sora_t2v", "sora_i2v"]:
            if elapsed_time_total < early_phase_duration:
                check_interval = early_phase_interval
                phase = "前期"
            else:
                check_interval = late_phase_interval
                phase = "后期"

        # ... 查询逻辑 ...

        # 累加等待时间
        if self.video_mode in ["sora_t2v", "sora_i2v"]:
            elapsed_time_total += check_interval
```

## 🚀 使用建议

### 1. 单任务使用
- **预期时间**: 1.5-3 分钟
- **查询次数**: 6-12 次（V1.0 为 18-30 次）
- **节省配额**: 约 50%

### 2. 批量任务使用
- **建议并发数**: 2-3 个任务
- **总查询次数**: 显著降低
- **服务器压力**: 明显减少

### 3. 监控要点
- 关注日志中的"前期阶段"和"后期阶段"标识
- 验证任务完成时间是否延迟（预期不会）
- 统计实际 API 调用次数

## ⚠️ 注意事项

1. **时间准确性**：累计时间基于查询间隔，可能存在 ±1 秒误差
2. **阶段切换**：3 分钟是理论值，实际可能在第 6-7 次查询时切换
3. **并发影响**：多个任务同时运行时，总体 API 调用次数减少效果更明显
4. **向后兼容**：不影响其他视频模式的查询策略
