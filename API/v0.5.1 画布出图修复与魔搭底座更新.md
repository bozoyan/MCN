## 一、问题与根因(应用日志实测定位)

用户画布出图(挂参考图,Qwen/Qwen-Image-2.1-Turbo)连续报「图片尺寸不受当前模型支持,请调整 size 后重试」,调整尺寸无效。应用日志(`ai.reveric.debug/logs/latest.log`)揭示服务端真实报错:

1. **画布(魔搭)**:`HTTP 400 "image file size exceed limit: 5242880"`——**参考图文件超过魔搭 image_url 的 5MB 上限**,与出图尺寸无关。错误消息含 "file size",被 `classifyAiImageError` 的通用 `contains('size')` 判定误分类为「尺寸不受支持」,文案误导用户反复调尺寸。
2. **MOSS 官方渠道**:`HTTP 400 "size requires dimensions 256..2048 divisible by 16, at most 2097152 pixels"`——应用内置的 MOSS 尺寸表 2K 档(如 2048x2048 = 4,194,304 像素)超出服务端 2,097,152 总像素上限,选了必挂。

## 二、修复内容

### 2.1 错误分类新增「参考图过大」(`image.dart` / `client.dart`)

- `AiImageErrorCode` 新增 `file_too_large`;`classifyAiImageError` 在通用 size 判定**之前**识别 `file size` / `file too large` 关键字(文件大小消息含 "size",不提前认出就会误报尺寸错误)。
- `imageErrorMessage` 新增文案:「参考图文件超过服务端大小上限,请压缩或更换参考图后重试。」
- 封面工作台失败文案穷举 switch(`slot_view.dart`)补 `file_too_large` 分支,新增 i18n 键 `editor.cover_error_file_too_large_title/body`(中英文)。

### 2.2 魔搭参考图发送前压缩到 ≤5MB(`client.dart` / `modelscope.dart`)

- `ImageClient` 新增共享入口 `imageInputAsDataUriWithinLimit(imageData, maxBytes)`:把 data URI / http(s) / 本地路径 / 裸 base64 统一还原为字节,超限时复用现有 `compressImageReference`(isolate 内缩图 + 逐档降质,`hardMaxBytes` 达标后才放行)重编码;解码失败抛既有的「参考图无法读取」错误。
- 魔搭客户端 `image_url` 全部走该入口(`_referenceMaxBytes = 5MB`),超 5MB 的参考图自动压缩后发送,画布图生图不再因文件体积被拒;服务端仍拒时错误分类给出准确提示。

### 2.3 MOSS 尺寸表收缩到服务端真实约束(`catalog.dart`)

总像素上限从 4,194,304 修正为 2,097,152,全部尺寸满足每边 256-2048、16 的倍数、总像素 ≤ 2,097,152:

- **2K 档重排**:1:1→1440x1440、4:3→1664x1248、3:4→1248x1664、16:9→1920x1088、9:16→1088x1920、3:2→1760x1168、2:3→1168x1760、21:9/9:21 保持 2016x864/864x2016;5:4/4:5 在上限内凑不出合法档(与 1.5K 重复或超限),从 2K 档移除,下拉自动不再展示该组合。
- **1.5K 档**:1:1 1536x1536(2,359,296 像素,超限)→ 1408x1408;其余档位均在限内保持。
- **1K 档**全部合法,保持不变。

### 2.4 魔搭底座清单更新为实测七个(`channels.dart` / `catalog.dart`)

按用户提供的魔搭实际可用底座清单调整(键为魔搭 Model-Id):

| 魔搭 Model-Id | 处置 | 尺寸表 |
|---|---|---|
| Qwen/Qwen-Image-2.1-Turbo | 保留 | 魔搭通用 13 比例 × 1K/2K |
| Qwen/Qwen-Image-2.1 | 保留 | 同上 |
| Tongyi-MAI/Z-Image-Turbo | 新增 | 同上 |
| krea/Krea-2-Turbo | 新增 | 同上 |
| MusePublic/flux-high-res | 新增 | 同上 |
| openmoss/MOSS-Image-SFT | 新增 | 复用 MOSS 收缩表(与官方 API 同一模型) |
| briaai/Fibo-2.0-dev | 新增 | 魔搭通用表 |
| Qwen/Qwen-Image-2.1-Pro / 3.0 / 3.0-Pro | 移除(平台已不可用) | — |

- `imageModelsCatalog` 新增 4 个条目(`z-image-turbo`、`krea-2-turbo`、`flux-high-res`、`fibo-2.0-dev`),默认尺寸 1024x1024;被移除 Qwen 型号的目录条目保留,兼容历史任务快照。
- 参数记忆/默认模型指向被移除型号时自动回落默认底座,已有容错覆盖。
- 聊天出图对话框默认模型 `Qwen/Qwen-Image-2.1-Turbo` 在清单中,不受影响。

### 2.5 魔搭建议采样步数按模型区分(API-Inference 文档核对)

用户提供的 `API-Inference.md` 官方文档明确:`steps` 对 `Qwen/Qwen-Image-2.1-Turbo` 应为 **8**,对 `Qwen/Qwen-Image-2.1` 应为 **50**;原参数面板对魔搭模型一律预填 steps=8,用 2.1 非 Turbo 底座时步数错误、出图质量受损。修正:

- `channels.dart` 新增 `modelScopeRecommendedSteps(modelId)`:仅对官方登记步数的两个 Qwen 底座返回建议值,其余底座返回 null **不猜值**(蒸馏模型步数过高画面崩坏、普通模型步数过低欠拟合,没有依据的值宁可留给服务端默认)。
- `ImageRequestExtrasPanel` 新增 `recommendedSteps` 入参:仅当已存参数没有 steps 时作为输入框初始值;留空即请求不带 `steps`,沿用服务端模型默认。引导系数 1.0、种子 -1 的预填保持。
- 四处入口接线:聊天出图对话框、人物拍照/头像弹窗、封面设计师参数区、画布「调节」按钮(新增 `modelId` 透传,由 image_composer 提供当前模型)。

## 三、魔搭 API 实测与文档核对记录(2026-10-31)

`API-Inference.md` 官方文档核对结论:size 平台通用约束 `[512x512, 2048x2048]`、LoRA ≤6 且权重和 1.0、异步任务/轮询头,均与现有实现一致;差异点为 steps 按模型建议值(见 2.5)。文档未给出各新底座专属尺寸约束,新底座继续挂魔搭通用 13 比例 × 1K/2K 表。

- 现有魔搭尺寸表抽查 `2048x1536`、`2048x1152`、`1512x648`、`1200x800` 全部受理成功——画布尺寸表本身没有问题,失败均为参考图超限。
- 新底座受理探测:`Z-Image-Turbo`、`Krea-2-Turbo` 对 1024x1024 / 2048x2048 / 2048x1152 全部受理;`flux-high-res` 对 1024/2048 受理(2048x1152 触发平台限流非参数拒绝)。
- `openmoss/MOSS-Image-SFT`、`briaai/Fibo-2.0-dev` 探测时被平台限流(rate limit / queue full),无法判定各自尺寸约束,按已知约束收保守表;若后续服务端报出新的约束,错误分类现在能准确显示原因。

## 五、遗留与说明

- 各新底座(尤其 Fibo-2.0-dev、MOSS-Image-SFT 魔搭版)的精细尺寸约束未逐一探测,当前统一挂魔搭通用表;个别底座若拒绝某尺寸,服务端错误现在会以真实原因显示,不再误报「尺寸不受支持」。
