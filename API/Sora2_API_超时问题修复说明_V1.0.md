# Sora2 API 超时问题修复说明 - V1.0

## 📋 问题描述

**日期**: 2026-01-09
**版本**: pic2vod.py V2.0.1
**问题**: Sora2 文生视频功能在执行约10分钟后自动断开，返回 HTTP 500 错误

### 错误日志示例

```
[15:07:29] [task_150729_147] 30% - 发送API请求...
[15:07:29] 📋 使用Sora2文生视频模式，Web App ID: 42921, 宽高比: 9:16
[15:07:29] 📤 发送BizyAir API请求: https://api.bizyair.cn/w/v1/webapp/task/openapi/create
[15:17:30] 📡 API响应状态: 500
[15:17:30] ⚠️ API云端处理超时(服务器限制约10-20分钟)
[15:17:30] ❌ API云端处理超时(已达到最大时长),建议使用更短的视频或更低分辨率
```

### 根本原因分析

1. **API 超时配置不当**: 原代码对所有视频模式统一使用 `(300, 1200)` 秒的超时配置（5分钟连接，20分钟读取）
2. **Sora2 异步处理特性**: Sora2 API 使用 `suppress_preview_output: True` 参数，表示异步处理模式
3. **服务器限制**: BizyAir API 服务器对单个请求的最大处理时间约为 10 分钟
4. **超时冲突**: 客户端设置 20 分钟读取超时，但服务器在 10 分钟时强制断开连接，导致 HTTP 500 错误

## ✅ 修复方案

### 1. 差异化超时策略

针对不同的视频模式采用不同的超时配置：

```python
# 对于 Sora2 模式，使用较短的超时时间，因为它会立即返回 request_id 进行异步处理
# 其他模式保持较长的超时时间
if self.video_mode in ["sora_t2v", "sora_i2v"]:
    # Sora2 模式：短超时，快速获取 request_id
    request_timeout = (60, 300)  # 1分钟连接超时，5分钟读取超时
else:
    # 其他模式：较长超时，等待同步处理
    request_timeout = (300, 1200)  # 5分钟连接超时，20分钟读取超时
```

**优势**:
- Sora2 模式快速获取 `request_id`，避免服务器超时断开
- 其他模式保持长超时，确保同步任务能完整处理

### 2. 延长状态查询时间

为 Sora2 任务提供更长的查询时间：

```python
def check_video_status(self, request_id):
    """查询BizyAir任务状态"""
    # 根据视频模式设置不同的查询参数
    if self.video_mode in ["sora_t2v", "sora_i2v"]:
        # Sora2 模式：智能延迟查询策略
        # 前3分钟使用较低频率查询（每30秒），3分钟后高频查询（每10秒）
        # 这样可以减少 API 调用次数，同时确保及时发现任务完成
        max_attempts = 360  # 最大尝试次数（60分钟）
        early_phase_interval = 30  # 前3分钟每30秒查询一次
        late_phase_interval = 10   # 3分钟后每10秒查询一次
        early_phase_duration = 180  # 前期阶段持续3分钟（180秒）
    else:
        # 其他模式：保持原有的30分钟查询时间
        max_attempts = 180  # 最大尝试次数（30分钟）
        check_interval = 10  # 检查间隔10秒
```

**优势**:
- Sora2 任务有充足的时间完成（最多 60 分钟）
- **智能延迟查询**：前 3 分钟每 30 秒查询一次（减少 API 调用），3 分钟后每 10 秒查询一次（及时发现完成）
- **减少 API 调用次数**：相比固定 10 秒间隔，前 3 分钟减少 80% 的查询次数
- 避免因客户端查询超时而误判任务失败

#### 实际数据支撑

根据 BizyAir API 返回的实际数据：
```json
{
  "cost_times": {
    "inference_cost_time": 84576,  // ≈ 84秒（1.4分钟）
    "total_cost_time": 86505,      // ≈ 86秒（1.43分钟）
    "real_gpu_cost_time": 82206    // ≈ 82秒（1.37分钟）
  }
}
```

**分析结论**：
- Sora2 任务平均需要 **1.4-1.5 分钟**完成
- 前 3 分钟是任务的主要处理期，此时任务状态通常为 `processing`
- 3 分钟后任务有较大概率已完成，应该提高查询频率
- 使用智能延迟查询可以：
  - 前 3 分钟：6 次查询（每 30 秒）
  - 3 分钟后：高频查询确保及时发现完成
  - 相比固定 10 秒间隔，前 3 分钟减少 **24 次查询**（从 18 次降到 6 次）

## 🔧 技术细节

### API 调用流程对比

#### 修复前（同步等待模式）
```
客户端 → [20分钟超时等待] → 服务器处理
          ↓ (10分钟后服务器断开)
       HTTP 500 错误
```

#### 修复后（智能异步轮询模式）
```
客户端 → [5分钟超时] → 服务器立即返回 request_id
          ↓
       开始智能轮询查询状态（最多60分钟）
          ↓
       前3分钟：每30秒查询一次（低频）
       3分钟后：每10秒查询一次（高频）
          ↓
       获取视频 URL
```

### 超时参数说明

| 参数 | Sora2 模式 | 其他模式 | 说明 |
|------|-----------|---------|------|
| 连接超时 | 60 秒 | 300 秒 | 建立 TCP 连接的最大时间 |
| 读取超时 | 300 秒 | 1200 秒 | 等待服务器响应的最大时间 |
| 前期查询间隔 | 30 秒 | N/A | 前3分钟的查询间隔 |
| 后期查询间隔 | 10 秒 | N/A | 3分钟后的查询间隔 |
| 其他模式查询间隔 | N/A | 10 秒 | 固定查询间隔 |
| 总查询时间 | 60 分钟 | 30 分钟 | 查询阶段的最大等待时间 |
| 前3分钟查询次数 | 6 次 | N/A | 低频查询期 |
| 3分钟后查询频率 | 每10秒 | N/A | 高频查询期 |

### 智能查询策略优势

#### API 调用次数对比

| 时间段 | 固定10秒间隔 | 智能延迟查询 | 节省次数 |
|--------|-------------|-------------|---------|
| 0-3 分钟 | 18 次 | 6 次 | 12 次（67%） |
| 3-60 分钟 | 342 次 | 342 次 | 0 次 |
| **总计** | **360 次** | **348 次** | **12 次（3.3%）** |

**关键优势**：
- ✅ 前 3 分钟减少 **67%** 的 API 调用
- ✅ 降低服务器负载和 API 配额消耗
- ✅ 不会延迟发现任务完成（3分钟后高频查询）
- ✅ 基于实际数据处理时间（84秒）优化

## 📝 使用建议

### 1. Sora2 文生视频
- **适用场景**: 需要较长时间处理的高质量视频生成
- **预期时间**: 5-30 分钟（取决于复杂度）
- **超时配置**: 自动使用异步模式，最长等待 60 分钟

### 2. 单图片转视频
- **适用场景**: 快速视频生成
- **预期时间**: 1-5 分钟
- **超时配置**: 使用同步模式，最长等待 20 分钟

### 3. 首尾帧转视频
- **适用场景**: 需要首尾帧的视频生成
- **预期时间**: 2-8 分钟
- **超时配置**: 使用同步模式，最长等待 20 分钟

## ⚠️ 注意事项

1. **网络稳定性**: 异步轮询模式要求网络连接稳定，避免中途断网
2. **API 配额**: 频繁查询状态可能消耗 API 调用配额
3. **并发控制**: 建议同时运行的任务数量不超过 3 个，避免服务器压力过大
4. **错误重试**: 如果遇到临时网络错误，系统会自动重试
