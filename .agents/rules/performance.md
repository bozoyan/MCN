# UI 重建与加载性能

## 高频 UI 状态与昂贵内容隔离

- 页面包含昂贵内容（大文本排版、分页测量、复杂图表、长列表布局等）时，时钟、状态轮询、滑块拖动、局部开关等高频 UI 状态**不得**放在同一父级重建范围内。
- 用独立 widget、`ValueNotifier` + `ValueListenableBuilder` 或等价的局部状态隔离无关更新，避免高频状态变更重建昂贵内容。
- 优化前先定位实际 rebuild 边界和昂贵计算路径；不要仅靠给子 widget 加 `const` 掩盖父级重建问题。

## 虚拟列表 Loading

- 虚拟列表 / 缓存范围会并行构建多个未就绪 item。禁止为每个 item 展示持续旋转的 loading 图标。
- 优先使用轻量骨架占位，并以短暂进入或内容切换动画反馈状态。
- 可复用的 loading / empty / error 纯展示组件应拆到独立文件。承载数据请求、状态选择和业务回调的容器只组合这些组件，不混入其具体视觉实现。

## 动画成本

- 动画必须有明确生命周期：进入和切换动画完成后停止；只有确实需要持续反馈的单一任务才保留循环动画。
- 不要为可同时出现的多个列表 item 维持独立的无限循环 ticker 或 shimmer。
- 新增动画前评估可见 item 数量、重绘范围和低性能设备的合成开销。

## 已有内容刷新时保持布局稳定

适用于后台同步、轮询、回到前台和手动刷新。首次无数据加载可展示占位；已有内容刷新时保留当前数据、筛选、选择和滚动位置，不清空页面或切回整页 loading。日期、数量等数据标签只随实际数据更新，不临时替换成“同步中”等过程文案，也不随 busy 改变颜色或尺寸。进度反馈放在原有固定尺寸的刷新图标或按钮内，禁止通过增删进度条、提示行或错误横幅挤动内容。刷新失败时保留可用内容并记录日志；确需用户处理的失败应提供不挤动布局的明确提示。桌面和移动端都要检查“空闲 → 刷新 → 成功 / 失败”及缓存重读过程；相同数据下，关键控件的位置、尺寸和滚动位置应保持不变。
