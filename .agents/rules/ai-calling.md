# AI 调用规则

- 复杂 AI 文本生成调用优先通过 `Agent` 进行，包括：多轮生成、工具调用、需要记忆/上下文管理、需要流式事件、需要子 Agent、需要统一运行态追踪的场景。
- 只需要一次轻量文本生成的场景可以直接使用 `chatCompletion`，例如短标题、简单分类、简短摘要、一次性 JSON/结构化输出；不要为了单次调用强行包一层 `Agent.custom()`。
- 禁止直接调用底层 ProviderClient；除非是在 `AiClient` / provider 适配层内部。
- **已有的 `chatCompletion` 调用不能擅自迁移成 `Agent`。** 如果认为需要迁移，必须先说明理由、影响范围和替代方案，并和用户确认后再改。
- 例外情况：嵌入向量生成（`AiEmbeddingService`）或纯 token 计数等非文本生成场景可以绕过此规则。
- Agent 的 `maxIterations` 根据工具需求设置：纯分析设 1，涉及工具调用设足够大（如 30）确保完整执行。

## 工具描述与 schema

### 降低模型调用成本

1. **原则：尽量避免特例。** 工具设计优先降低模型理解成本、减少模型犯错机会，不为维持形式上的语义区分增加调用门槛。
2. **方式：兼容易错调用。** 对模型容易混淆的调用方式，优先在工具实现中兼容并复用统一的校验和执行逻辑，减少要求模型记忆的特例说明。
3. **单例资源：Create / Write 等价，也支持直接 Edit，不可 Remove。** Create / Write 操作同一份资源，不产生额外实例。无需在常驻 prompt 中解释“单例”或逐项强调这些特例；实际调用不支持的操作时，返回明确错误即可。

### 工具说明保持契约级别

AI 工具描述只说明模型完成调用所需的参数、边界和结果；不要把内部落库、版本、身份或实现流程写进 prompt，除非它会直接改变下一步调用方式。判据是「删掉这句，模型这次调用会不会做出不同选择」——不会就删。典型违规：叙述系统内部如何判定（「由系统按章号水位判定」）、内部存储手段（软删/硬删、直写 DB、working overlay、已索引、持久化）、内部算法（「广度优先搜索」）、谁在维护数据（「由用户在 UI 中变更」）、运行时机制（「立即返回不阻塞回合」）。改成模型可观察的事实：字段必填与取值、返回哪些键、什么情况下报什么错、该改用哪个工具。适用于所有 `_xxxDescription`、input schema 的 `description`，以及由它们生成的 `_CollectionSchema.fieldDescriptions`。

### Description 不重复 schema

tool description 禁止复述 input schema 已有的内容。单个参数的必填、默认值、取值范围、枚举和含义只写在 schema 的 `description` 里——参数说明跟着参数走，模型看到字段时就看到它的说明；工具描述里那份「输入：- xxx（必需）：...」清单一律删除。description 只写 schema 表达不了的东西：工具做什么、何时用、跨字段约束（「kind=prompt 时 prompt 必填」）、路径语法、返回结构、完整调用示例。删除前先确认该细节在 schema 里存在，缺了就先补进 schema 再删，不能连信息一起丢。

### Tool schema 保持静态

禁止按运行时状态、用户数据或环境事实动态修改、裁剪或重建 AI tool schema；这会破坏工具定义缓存与调用契约。确有必要时，先说明原因、缓存与兼容性影响，并获得用户明确确认后再改。
