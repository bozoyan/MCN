# Widget 拆分规则

配合 `AGENTS.md` 工作契约中的“边界优先”使用：根契约规定「该由谁拥有」，本文件规定「何时必须停手拆」与「怎么拆才不是假拆」。新增 widget、往现有 page/panel 加状态、或抽取子组件前先读这里。

## 可数信号（命中即停，先拆再继续）

判断「该拆了」不靠感觉，靠可数阈值。任一命中即停下拆 region，不要等文件变大：

- 单个 widget 的 `useState` + `useMemoized` + `useRef` **> 10 个**。
- 单个 `build` 方法 **> 800 行**。
- 单个抽取的 widget / 函数需要 **> 5 个参数**（见下「参数袋」）。

超过 10 个 co-located 状态时，往下加的每一个状态都在制造未来必付的复利税：状态越交织，之后抽任何东西都越贵。

## 反面教材（只读，勿模仿、勿改）

`lib/desktop/pages/novel_editor.dart`：一个约 5400 行 `build`、62 个 co-located 状态、72 个 build 内局部函数的 god-widget。它用 7 个 `part` 文件切分，但都是 `part of` 同一私有作用域——**假边界**。它是本规则存在的理由，不是可参考的范式。不要因为「现有大文件就这么写」而复制它的结构。

## `part of` 不是模块边界

`part of` 让子文件共享宿主的整个私有作用域，任何 helper 仍能触及全部状态，因此**不构成边界**。

判据：**抽出去之后还得把一坨状态当参数传回来**，就说明边界是假的。真正的边界是一个有显式构造参数、自己持有那一片状态的独立 `Widget`（或 Notifier），而不是 `part of`。用 `part` 只是把行数挪走、把问题藏起来。

## 参数袋 = 边界没想清

抽取时子组件/函数需要 **> 5 个参数**，停。两条出路：

1. 把语义内聚的一组值（尤其多个 `ValueNotifier` + 操作它们的回调）合并成一个**带方法的对象**，向子组件暴露行为而非裸状态。
2. 把这些状态直接放进子 widget，让它自己 `useState` / 持有，父级不再转发。

不要靠堆 `required` 参数硬抽（那只是把 god-widget 换个位置）。

## 按关注点归位，不要六合一

god-widget 的本质是多个不同关注点挤在一个 build 里。拆时按关注点各归各家，**不要用一个巨型 state 对象替换一堆 useState**（那只是改名，一样不可推理）：

| 关注点 | 归宿 |
|---|---|
| 多字段编辑 + 校验 + 提交/重置 | `lib/third/form`（见 `form.md`） |
| 导航 / 视图模式的多字段联动转移 | 一个 region 级 `Notifier` / reducer（一簇一个，不是全局巨 store） |
| 多步 DB / 文件 / 网络 / AI 写编排 | `Orchestrator`（见 `service-naming.md`） |
| 跨页面共享状态 | Riverpod provider（见 `state-management.md`） |
| 纯展示区域 | 独立 region `Widget`，自持局部状态 |

reducer 和 form 都只是「某一簇」的解，不是给整个 god-widget 的银弹。根因永远是缺 region 边界，不是缺某个状态管理工具。

## 存量 god-widget 处理

对已存在的大 widget：**新增只进新 region，不再往旧 `build` 加状态**。让它停止恶化，而不是要求一次性重写。是否增量拆解由任务显式决定，不在常规改动里顺带做（与根工作契约的“最小且遵循现状”一致）。
