# Web 工具按需浏览器加载方案

> 状态：暂缓实施，仅归档调研和建议。用户于 2026-10-03 决定等实际需要出现后再评估。
> 本文不代表已批准接入 WebView、搜索 API 或新增浏览器界面。
> 调研与包体积测量日期：2026-10-03。插件版本和平台要求在重新启动方案时复核。

## 1. 背景与已有处理

当前会话工具在 `lib/shared/services/ai/tools_web.dart` 中实现：`WebSearch` 请求百度搜索 HTML 并解析结果；`WebFetch` 通过 HTTP 读取网页，将 HTML 转为 Markdown，最多返回 10,240 字符。

一次 Debug 调研子会话暴露了内容有效性问题：

| 调用 | 观察结果 |
| --- | --- |
| 29 次 WebSearch | 前 7 次有结果，后 22 次返回空列表，均记录为成功 |
| 41 次 WebFetch | 40 次记录成功，1 次百度跳转解析失败并正确记录错误 |
| 上述成功的 WebFetch | 至少 7 次缺少有效正文：百度百科只返回标题、起点为空、4 次 DuckDuckGo 验证页、1 次豆瓣 JS 验证页 |
| 内容截断 | 28 次返回被截断；整页导航、登录入口等也占用字符预算 |

DuckDuckGo 和豆瓣的保存结果可以确认是反爬验证页面。百度连续空结果缺少当时的原始 HTML；复查时搜索页恢复正常，不能认定那 22 次全部由反爬或限流造成。

本次排查已在工作区修正错误识别、无响应类型时的 HTML 识别及 UTF-8 解码。验证码页、空正文和无法识别的搜索响应会返回明确失败，真正的无匹配结果仍可返回空列表。这部分验证结果为 21 个测试通过、静态分析通过，真实联网测试未运行。它与本文暂缓的 WebView 接入是两项独立工作，归档不表示这些修改已经发布。

## 2. 暂缓原因与重新评估条件

目前只有一次会话的故障样本和 macOS 包体积实验，尚无目标站点的 WebView 成功率、耗时或内存实测。增加浏览器会带来实例生命周期、平台差异、Cookie 管理和 Windows 运行时分发成本，暂不加入项目依赖。

出现以下情况时，由项目维护者重新评估：

- 正确识别失败后，资料调研仍反复因必要页面无法读取而中断，且找不到可用替代来源。
- 样本表明主要缺口是 JavaScript 渲染或脚本跳转，普通浏览器能够读取同一页面。
- 用户明确需要在应用内打开网页、完成验证并继续提取资料。

重新评估时先用同一批页面比较 HTTP 和 WebView 的有效正文获取率、耗时及资源消耗。只有确认浏览器能补回必要内容，才决定接入；如果主要限制来自交互验证码或站点访问限制，继续扩大后台浏览器调用不构成解决方案。

## 3. 推荐方向与取舍

推荐保留 HTTP 快速路径，仅为需要浏览器能力的页面增加按需加载。

| 方案 | 判断 |
| --- | --- |
| 现有 HTTP 加明确失败诊断 | 暂缓期间继续使用；不执行页面 JavaScript |
| HTTP 加按需 WebView | 未来优先验证，针对动态正文、脚本跳转和需要保留会话的页面 |
| 所有搜索和抓取都使用 WebView | 不采用为默认路径；引入额外渲染和生命周期成本，仍可能被拦截 |
| 正式搜索 API | 搜索稳定性不足时单独评估；需要验证中文结果质量、费用和凭据管理，不在本次预选供应商 |
| 随应用打包完整浏览器内核 | 不作为默认分发方式；优先使用平台提供的 WebView 或共享运行时 |

### 3.1 WebFetch 的候选流程

1. 先执行现有 HTTP 抓取及内容有效性检查，普通页面直接返回。
2. 仅对可由浏览器补足的情况尝试一次 WebView，包括动态页面空壳、未解析的脚本跳转或可在浏览器中继续的验证页。HTTP 404、参数错误等直接失败。
3. 等待目标正文出现或达到总超时，随后在同一 WebView 中读取最终 URL、标题和正文。不能只凭加载完成事件认定动态正文已经就绪，也不应在浏览器加载后再用独立 HTTP 请求重抓。
4. 提取并校验正文后，再按既有字符限制截断。保留 `truncated`、字符数和错误状态的真实含义。
5. 仍然是交互验证码时结束本次自动调用，明确返回需要人工验证；不自动连续重试。是否提供手动打开入口，取决于后续用户需求，不能让后台工具无限等待一个不可见页面。

浏览器实例按需创建，受工具取消和超时控制，完成后释放。首版若启动接入，同一站点只允许一个浏览器任务在执行，避免并发放大站点验证；排队任务也必须可取消。使用应用自己的 WebView 会话，不假定能继承用户 Chrome 或 Safari 的登录状态。

若以后增加人工验证，验证和正文读取应使用同一浏览器会话。不能先在独立浏览器完成验证，再假定 Cookie、设备环境和网络身份已同步到 HTTP 客户端。

### 3.2 搜索与正文提取

`WebSearch` 的主要职责仍是返回结构化搜索结果。浏览器能渲染搜索页，但不会消除站点限流，也不会让依赖网页结构的解析器永久稳定。未来优化优先考虑同站点排队、相同查询合并和短期缓存；明确拦截后暂停该来源，避免继续发出大量相同性质的请求。

正式搜索 API 是独立决策。若选择收费服务，由维护者确认供应商、中文检索效果和预算后再设计配置，不为本文预先新增 API Key 设置或后端代理。

文章页可以在 DOM 副本中提取正文，再复用 Markdown 转换。搜索列表、百科条目和书籍详情页要分别验收，不能默认文章提取器适合全部页面。正文提取器的包体积和实际抽取效果未包含在本次测量中。

## 4. 平台实现与分发

候选插件为 `flutter_inappwebview`。调研时稳定版为 6.1.5；它提供后台 WebView、JavaScript 执行和 Cookie 管理。[原生实现说明](https://inappwebview.dev/docs/intro/#native-webview-implementation)、[后台 WebView 文档](https://inappwebview.dev/docs/webview/headless-in-app-webview/)

| 平台 | 浏览器能力来源 | 包体积与接入影响 |
| --- | --- | --- |
| Android | 系统的 `android.webkit.WebView` | 无需把完整 Chromium 内核打进 APK；增量来自插件、AndroidX、Dart 代码和资源，尚未实测 |
| iOS | 系统的 WKWebView | 无需随应用打包浏览器内核；尚未验证构建和体积 |
| macOS | 系统的 WKWebView | 已做基础接入 Release 体积测量，见第 5 节 |
| Windows | WebView2 Runtime | 优先共享 Evergreen Runtime，缺失时引导下载安装；插件本身的安装包增量尚未实测 |
| Linux | 该插件所列支持平台不包含 Linux | 保留 HTTP 和明确失败，不承诺浏览器增强能力；若 Linux 有实际需求，另评估实现 |

Windows 使用 WebView2 不要求随应用携带完整浏览器。Evergreen 模式由多个应用共享运行时，推荐在安装或首次使用前检查是否存在，缺失时引导安装。微软提供约 2 MB 的在线安装引导程序，也允许按需下载该引导程序；这 2 MB 不包含随后下载的完整 Runtime。离线安装器或固定版本分发才需要随包携带完整运行时。不能把 Edge 浏览器已安装等同于生产环境的 WebView2 Runtime 可用。[微软分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

macOS 实验所用插件实现 1.1.2 仍依赖 CocoaPods，本次与项目现有 Swift Package Manager 混合构建成功。锁定的 Flutter SDK 提示，插件缺少 SPM 支持在未来版本可能成为错误；正式接入前复核候选版本，不把实验版本永久锁成方案要求。

各平台的后台实例转可见页面能力存在差异，不能仅凭 macOS 成功就承诺 Windows 或移动端行为一致。WebView 能执行脚本并保留 Cookie，但仍可能无法通过站点验证。Cloudflare 的文档可作为此类限制的参考，不表示本次出错的网站使用了 Cloudflare。[WebView 集成要求](https://developers.cloudflare.com/turnstile/get-started/mobile-implementation/)、[浏览器支持边界](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)

## 5. macOS 包体积实测

两次构建使用相同源码快照和项目锁定的 FVM SDK，产物均为 x86_64 与 arm64 通用 Release 包。仅实验版本新增 `flutter_inappwebview 6.1.5` 及相关依赖，原有锁定依赖版本未变。实验入口实际引用后台加载、JavaScript 正文读取、标题与 URL 读取、Cookie 管理和实例释放，避免只加入依赖却被编译器裁掉。

单位采用十进制 MB，即 1 MB 等于 1,000,000 bytes。

| 产物 | 引入前 | 引入后 | 增量 | 增幅 |
| --- | ---: | ---: | ---: | ---: |
| 解压后 `.app` | 151.08 MB | 156.01 MB | 4.93 MB | 3.26% |
| ZIP | 67.64 MB | 69.07 MB | 1.43 MB | 2.11% |
| DMG | 74.64 MB | 76.22 MB | 1.58 MB | 2.11% |

未压缩增量中，WebView 原生插件约占 4.320 MB，OrderedSet 依赖约占 0.313 MB，App.framework 约占 0.296 MB。

测量边界：

- 两次 Release 构建均成功，未启动探针应用，未实测目标网站抓取效果。
- 未包含最终交互界面、Readability 或完整工具编排代码，数值表示基础接入成本。
- ZIP 使用 `ditto`；DMG 使用 `hdiutil`，两组均采用 HFS+、UDZO 压缩并包含 Applications 链接。因本机 appdmg 的 Node 原生模块版本不匹配，未制作正式 Finder 布局和公证发布包。
- 主工作区没有引入 WebView 依赖。Android、Windows、iOS 和 Linux 未进行对应的体积构建，不能套用 macOS 数值。

### 验收与数据分析

使用同一批必要页面比较 HTTP 与候选 WebView 路径，至少包含静态新闻页、JS 渲染页、脚本跳转、真实无搜索结果、验证码页和失效 URL。验收记录区分自动获取成功、人工介入和明确失败，不以 HTTP 200、页面加载事件或非空字符串作为成功标准。

核心指标为有效正文获取率、单次耗时、浏览器实例数、内存变化及人工介入次数。数据先来自本地受控样本和现有调用日志；由实施者提交对照结果，维护者决定是否值得发布，不在本方案中预建埋点或新增诊断数据表。

必须验证取消、超时和页面关闭后实例释放，多个会话互不读取对方页面；普通 HTTP 成功路径不初始化浏览器。Windows 分别验证已安装与未安装 Runtime；Android、iOS、macOS 分别做真实设备或对应系统环境验证。

本次已执行的验证只有前述工具测试、静态分析和 macOS 体积构建。未来实现后的测试仍需串行使用 `fvm flutter test`，并重新执行各目标平台的 Release 构建和页面读取验收。移除增强能力时可退回 HTTP 与明确失败路径，不应涉及用户业务数据迁移。
