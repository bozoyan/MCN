# 会话历史保留与清理方案

日期：2026-09-08。

状态：PR-1 与 PR-2 的基础实现已在本次会话中完成。2026-09-08 根据用户要求，将可确定作品归属的过期孤儿会话、消息和 Todo 纳入清理方案；孤儿清理扩展已实施并通过定向回归。清理继续后台运行并保护在用作品，AskUser 不成为清理模块的业务依赖。

文档档位：完整档。清理与 AskUser 是两个可独立交付的改进，不互为实施依赖。本次实施孤儿清理扩展；本节新增验证记录不代表重新验证 AskUser 或双端 UI。

## 1. 背景

### 现状与问题

原清理实现分别按 session 更新时间和 message 创建时间删除，曾留下关联残留并截断近期会话的旧消息。PR-2 基础实现已改为整树清理，并移除两个无调用的 `deleteOlderThan()` 旧入口。

现有 `AiSessionPersistenceService.deleteSession()` 仍只硬删指定 session，可能留下子会话、消息和 Todo。基础清理实现会逐轮警告并跳过失去父记录的子会话。本次扩展将可归属、已过期的孤儿数据纳入同一维护流程，覆盖既有残留及后续手动删除产生的残留。

设置标题已改为“历史记录保留时间”，下方说明文案已按用户要求移除。基础清理日志已输出实际删除数量；本次补充孤儿清理分组及异常诊断规则。

改动前，交互式 AskUser 通过内存 Completer 等待用户回复，没有等待期限。现有 chat 已通过应用前台状态和 session 可见性发送后台完成通知，可复用其判断及通知服务。用户已确认 AskUser 在未查看会话时立即通知，等待 10 分钟再次提醒，30 分钟自动选择推荐项或返回未回答，让 Agent 继续。

### 约束

- 清理后台运行，不阻塞应用启动；桌面与移动端均须覆盖页面进入、离开和后台运行。
- 清理判断集中在维护层、DAO 与作品生命周期边界，不渗入发送、保存、Todo、Agent 或页面缓存。
- 不新增数据库表、schema version、会话清理状态列、通用删除 Orchestrator 或 AskUser 跨重启恢复框架。
- AskUser 工具 schema 保持静态，复用现有通知能力，不新增平台权限或后台常驻服务。
- 正常过期会话树关联 Todo 的硬删除已获用户确认。用户本次要求扩展孤儿清理方案；`.agents/rules/data-deletion.md` 已同步为第 5.2 节限定的可归属孤儿集合，不扩大到订阅、附件或归属不明的数据。本次实现与测试不执行真实业务数据删除。

## 2. 目标

### 目标

1. 正在打开、已打开或仍有后台 Agent 运行的作品，其会话及内容库历史不被自动清理。
2. 按完整会话树或第 5.2 节定义的孤儿清理组判定过期，session、message、Todo 与命中的 active 指针使用同一集合，不截断仍有近期活动的组。
3. 作品打开与清理提交交错时，用户读不到跨库清理的中间状态；失败后重试仍重新核对活动状态。
4. 保留天数在读取、提交和执行层统一为 7 至 365 天，默认 30 天；日志能核对实际删除数量。
5. AskUser 按即时通知、10 分钟提醒、30 分钟自动处理运行，回答、取消、超时只生效一次，Agent 收到明确结果后继续。

### 非目标

不恢复已删除的父会话、不重写父子关系、不改手动删除交互；归属不明的孤儿、循环及跨作品冲突暂不自动删除。不扩大为加载失败的全链路重构，不据此判断某个历史事故的原因。不删除作品正文、记忆、用量、附件或其他保留资源；不承诺跨库原子提交、移动端后台准时唤醒或 AskUser 重启续答。

成功信号及对应测试统一列于第 6 节，避免重复维护验收清单。

## 3. User Stories

1. 作为作者，我希望打开的作品及后台生成中的会话保留完整历史，切到设置或关闭聊天区域也不会丢失正在使用的记录。
2. 作为作者，我希望未使用的过期会话连同子会话一起清理，删除父会话后留下的过期历史也能回收；近期会话仍能查看较早的消息。
3. 作为作者，我离开会话后希望及时收到提问通知；一直没有回复时，AI 按推荐项或现有上下文继续，并明确显示自动处理结果。
4. 作为维护者，我希望清理失败后保留可重试的主记录，并能通过阶段和数量日志判断未完成范围。

## 4. 解决方案

### 方案对比与决策

| 议题 | 方案 | 收益与代价 | 结论 |
| --- | --- | --- | --- |
| 清理范围 | 作品保护，按完整会话树清理 | 保留在用数据和树内一致性；长期打开的作品会延迟清理 | 采用 |
| 孤儿清理 | 缺失父 ID 下的子树与残留资源组成一组，复用保护及过期判定 | 可回收历史孤儿；需核实作品归属和缺失 ID 的保留引用 | 采用 |
| 孤儿清理 | 发现主记录缺失即逐行删除 | 会绕过活动时间、后台运行及关联保护 | 放弃 |
| 清理范围 | session 与 message 各按自身日期删除 | 实现简单，但会留下关联残留并截断近期会话 | 放弃 |
| 清理协调 | 在发送、保存和各类业务写入前检查删除状态 | 覆盖面大，但业务依赖增加且容易漏入口 | 放弃，协调仅放在打开与维护边界 |
| AskUser | 10 分钟提醒，30 分钟按推荐项或未回答结果继续 | 符合已确认的自主推进要求；自动结果必须标明来源 | 采用 |
| AskUser | 默认无限等待并持久化恢复执行 | 可跨重启续答，但需保存执行位置、上下文及副作用状态 | 本轮放弃 |
| AskUser | 超时只返回取消并要求任务停止 | 可结束等待，但不符合已确认的继续执行要求 | 放弃 |

继续后台定期清理，不阻塞应用启动。以作品为保护边界：作品正在打开、已经打开，或仍有后台 Agent 运行时，跳过该作品的全部 session、message 和会话关联资源。

只有未打开、没有后台运行的作品才进入会话过期检查。再以完整会话树或孤儿清理组为单位判定与清理，不单独删除近期会话里的旧消息。

代价是长期打开的作品会延迟清理。这个取舍优先保障正在使用的数据，不保证到达保留天数后立即删除。

清理改动集中在清理模块、必要的 DAO，以及作品打开/关闭的生命周期边界。发送、保存、Todo、Agent 和页面缓存不增加删除判断，不新增会话清理状态列或通用删除 Orchestrator。用户另外要求的 AskUser 超时通知只改问答自身的等待流程，不将清理判断塞进问答或 Agent。

### 关键假设

| 假设 | 如果不成立 | 应对 |
| --- | --- | --- |
| 作品入口能在首次内容读取前登记打开意图 | 清理与打开发生竞争 | 入口接线和生命周期测试通过后才启用对应清理路径 |
| 后台请求可由打开作品、运行集合或保留引用识别 | 尚未进入运行集合的任务可能被遗漏 | 跳过可识别的候选范围，核对无归属入口，不宣称运行列表全覆盖 |
| 已确认的推荐标记足以驱动超时自动选择 | 推荐可能不符合用户最终偏好 | 明确显示自动来源，保留手动回答和取消入口；无推荐不猜答案 |
| 操作系统允许应用在时间点执行 | 移动端挂起导致提醒或自动处理延迟 | 恢复时按原截止时间处理，通知失败不阻塞结果 |

## 5. 方案实施

### 5.1 模型与关系

沿用现有作品、会话、消息和 Todo 模型，以会话父子关系得到完整树。缺失父 ID 只作为内存中的分组键，不补建 session、不修改 `parentId`，不新增持久化清理实体。作品打开引用计数和短期清理许可属于维护层运行时状态。

```text
作品
  └─ 1:N 会话（主库）
       ├─ 1:N 子会话（递归，主库）
       ├─ 1:N 消息（内容库）
       └─ 1:N Todo（主库）
内容库 active_chat_session ── 指向一个会话
远程订阅 / active 工作变更 ── 引用会话并阻止清理
```

关系图表达业务关联，不引入数据库级联约束。具体删除与保留规则见 5.3。AskUser 沿用请求和结果模型，扩展超时来源与未回答题目字段，契约见 5.5。

### 5.2 清理流程：保护、协调与候选判定

#### 作品已打开的定义

作品正被任一窗口、页面或保留的导航页面使用，就算已打开；不是仅看当前高亮的标签。切到设置、弹出对话框、折叠聊天区域或应用切到后台，都不解除作品保护。

作品入口在第一次内容读取前登记“正在打开”，作品所有使用页面退出后才释放。使用引用计数处理同一作品被多个页面使用的情况，不能在一个页面退出时错误解除其他页面的保护。移动端直接进入聊天和其他 AI 模式的入口也要覆盖，不能只登记小说编辑页。

当前 `novelContentDatabaseProvider` 使用 `keepAlive`，数据库缓存可能在页面关闭后继续存在，因此不以缓存是否存在判断作品是否打开。`WorkspaceNavigation` 是一次性导航请求，也不代表打开的作品集合。

保护集合由两部分组成：

- 作品生命周期边界维护的“正在打开或已经打开”的作品集合。
- 现有 `AiModeProcessingTracker` 中运行 session 对应的作品集合；只读复用既有运行状态，不让发送代码另报一套清理状态。

现有远程订阅仍引用的会话另外保守跳过。父会话页面关闭但 Agent 继续执行时，不能因页面退出就删除它。

#### 打开与清理协调

仅在每轮开始读取一次打开列表不够。可能发生：清理检查作品未打开，随后用户打开作品，清理仍按旧结果删除。

在维护层设置作品级协调入口，只连接作品进入边界与清理服务，不要求每次发送、保存或 Todo 操作取锁：

1. 用户开始打开作品，先登记打开意图。尚未取得清理许可的任务看到该意图后跳过作品，用户继续进入。
2. 清理可以在许可之外完成候选扫描，但删除每棵树或每个孤儿组前必须取得该作品的短期清理许可，重新检查打开意图、后台活动及数据库候选状态。
3. 清理已取得许可时，新打开的同一作品只等待当前树或孤儿组的事务操作完成，再读取数据；不能读到主库和内容库之间的中间状态。
4. 释放许可后优先处理打开意图，不继续批量占用作品。整库扫描、跨作品遍历、网络请求和备份都不能放在许可内。

这不是启动屏障，也不对正在打开的作品做清理。只在极少数“用户恰好打开正在提交清理的作品”的情况下等待当前事务结束。实际等待时长要通过测试和日志确认，不承诺未经测量的毫秒数。

后台新运行的来源也要在实施时核对：来自已打开作品的请求受作品保护；已有远程订阅的会话受引用保护；子 Agent 受父运行保护。发现没有这些归属的后台入口时，先跳过其可识别的候选范围，不能声称现有运行列表覆盖了所有异步启动窗口。

#### 会话树过期判定

先按保护作品集合排除候选，再按完整会话树处理。查询不使用 UI 的分页列表，后代不限一层。跨作品关系和循环继续跳过；已经失去父记录的子会话按下节规则进入孤儿清理组。检查主记录是否存在时包含软删除记录，不能用 UI 列表中不可见代替物理缺失。

会话树的最后活动时间取树内 session 更新时间、message 创建时间和 Todo 更新时间的最大值。清理模块直接查询实际数据，不要求业务保存代码额外更新父会话时间。整棵树都超过保留期限才清理；近期会话的旧消息全部保留。

仍有 active 工作变更或本地远程订阅时，跳过整棵树。此处不把待办状态等同于 Agent 运行状态。

持久化的 active 指针只是上次停留位置，不单独构成永久保护。作品关闭且会话树过期时可以清理，并条件清除该指针。

沿用一次固定的截止时间及 Unix 秒存储。系统日期错误仍可能影响过期判定，本轮不新增服务器校时或时钟监测体系。

#### 孤儿分组、归属与过期判定

清理单位分为三类，使用相同的保留天数和固定截止时间：

| 类型 | 分组方式 | 最后活动时间 |
| --- | --- | --- |
| 正常会话树 | 顶层 session 及全部后代 | session 更新时间、message 创建时间、Todo 更新时间的最大值 |
| 缺失父会话的孤儿组 | 以第一层缺失的父 ID 为分组键，合并所有直接子会话、全部后代，以及该缺失 ID 自身的消息和 Todo | 组内仍存在的 session、消息和 Todo 的最后活动时间最大值 |
| 无任何 session 节点的残留组 | 主库中物理不存在的同一个 session ID 对应的消息、Todo 和 active 指针 | 消息创建时间、Todo 更新时间的最大值；仅剩 active 指针时使用该状态行更新时间 |

例如父会话 P 已删除，但 A、B 的 `parentId` 都是 P：P 的残留消息和 Todo、A 和 B 及其全部后代共同接受过期判定。A 的近期活动会保护整组，不能先删除 B 或 P 的残留。若只有一个失去父记录的子树，也按同一规则处理。

作品归属必须来自明确关系：仍存在的子会话的 `novelId`、消息所在内容库对应的作品，或该内容库中的 active 指针。许可外扫描已登记的作品内容库，仅取 session ID、聚合时间和必要指针，不加载消息正文；同一缺失 ID 的所有证据必须指向唯一作品。需纳入仍有登记路径的软删除作品，不能将未检查的内容库视为空库。扫描失败或库缺失时，无法完成归属核对的孤儿组本轮跳过，不自动创建数据库文件。

`todos` 没有 `novelId`。仅剩 Todo、没有 session、子会话、消息或 active 指针作为归属证据时，保留并计入 `unattributed`，不从 metadata、标题或最近打开作品猜测归属。不同内容库出现同一个 session ID、父子跨作品或环形关系时同样跳过；这些情况不属于可自动清理的正常孤儿组。

每组的检查 ID 集合同时包含缺失的父 ID 和所有存活后代 ID。订阅、active 变更或运行集合命中其中任意 ID，整组保留。不能因缺失 ID 无法关联到 session 行而漏掉保护；运行 ID 无法确定作品时，沿用当前清理器的保守跳过行为。active 指针本身不构成永久保护，仅用于归属和条件清空。

取得所属作品的许可后，重新核实父记录或 session 仍物理缺失、子树成员及作品归属证据未变、全组仍过期且没有新增引用或运行。记录恢复、出现新活动、出现打开意图或分组结构变化时，放弃旧候选，下轮重新扫描。跨内容库归属扫描在许可外完成；作品库清单变化或本轮扫描不完整时，不在许可内补做全库扫描。

正常会话树与孤儿组必须互斥分组，每个 session ID 每轮最多处理一次。新发现的过期孤儿可以在本轮清理，不额外要求等待一个保留周期；新消息、Todo 或存活子会话则会按其实际活动时间保护整组。

#### 未落库状态与 7 天下限

普通短暂状态包括桌面 800 毫秒的延迟保存、正在流式生成的消息，以及含 pending/running 工具调用的消息；持久化代码明确过滤后两者。它们不等于历史消息正常情况下会在内存停留 7 天。

必须区分“本轮新消息尚未落库”和“数据库最后活动时间超过 7 天”：旧会话刚开始新一轮时，二者可以短暂同时成立。但普通页面发送受已打开作品保护；无页面的 headless 入口已先保存 seed，再执行 Agent。因此不为这些短暂窗口新增业务状态或保存协议。

原交互式 `AskUser` 等待 Completer 完成，没有超时，可能长时间挂起。PR-1 按 5.5 节增加有期限的等待和通知。清理端最多只读复用现有运行集合，不为 AskUser 新增清理心跳、活动上报或保活协议。自动后台 headless 入口已有自动取消 AskUser 的处理，不改成等待人工回复。

### 5.3 关联资源与删除顺序

| 资源 | 自动清理行为 |
| --- | --- |
| `ai_chat_sessions` | 删除正常过期树或孤儿组中仍存在的会话记录，不补建缺失父记录 |
| `ai_chat_messages` | 按同一批 session ID 删除全部消息，停止独立按消息日期清理 |
| `todos` | 按同一批 session ID 删除，包含可确定作品归属的孤儿组；仅剩 Todo 且归属不明时保留 |
| `novel_states.active_chat_session` | 仅当值属于删除集合时，在内容库事务中清除 |
| `session_subscriptions` | 有订阅就跳过，不新增订阅硬删除 |
| `working_changes` | active 改动保护会话树；其他记录沿用自己的历史策略 |
| 提交与提交明细 | 保留原来的成组清理策略，不随聊天直接级联 |
| 章节、大纲、角色、地点、画布等作品数据 | 保留，不回滚已经执行的工具改动 |
| 记忆、用量、计费与匿名上报 | 保留，来源 ID 作为历史信息 |
| 图片、附件、备份和分享产物 | 保留，不按聊天引用删除文件 |
| 独立的首页与远程 Assistant 表 | 不纳入本轮聊天清理 |

孤儿扩展增加可归属、整组过期的 session/message/Todo 关联清理路径。实施时同步 `.agents/rules/data-deletion.md` 的具体例外，不新增 `session_subscriptions`、附件或归属不明 Todo 的硬删除范围。

手动删除入口维持现状；它产生的残留与既有历史孤儿都在后续维护轮次按上述规则处理。孤儿不再永久排除，但仍须通过归属、活动时间和保护检查，不能仅凭主记录缺失就删除。

#### 提交与失败路径

对正常会话树和仍有 session 节点的孤儿组，确认内容库文件真实存在，取得作品级清理许可并复核保护条件后执行：

1. 内容库事务中按集合删除消息，条件清除命中的 active 指针。失败则回滚该事务，不删除主记录。
2. 内容库成功后，在主库事务中删除对应 Todo、子会话与根会话。主库成功才把整棵树计为完成。
3. 释放作品许可，处理等待的作品打开请求，不主动导航、不刷新整个应用。

两个数据库不是一个原子事务。本轮不新增持久化清理任务或生命周期列；主库失败或进程在两次提交之间退出时，保留过期主记录，下一轮可按原有时间条件再次选中并幂等清理。

异常中断后可能暂留消息已清空的过期会话，但不会先删掉主记录再留下继续运行的旧 ID。这个失败边界必须记录在日志中，不能宣称跨库同时提交或自动恢复已删除历史。

主库失败后等待进入作品的请求可以继续读取现存主记录；若用户产生新的活动，后续过期复核必须保护它，不得按上次失败时的旧候选集合继续删除。

无任何 session 节点的残留组采用相反的跨库顺序：先在主库事务中删除该组 Todo，再在内容库事务中删除该组消息并条件清空 active 指针。两个阶段都完成才计为完成，许可覆盖两个阶段。这样主库失败时内容库不变；内容库失败时仍保留消息或指针作为作品归属证据，下轮可重新发现并复核。不能先删掉唯一的内容库归属证据，再留下无法归属的 Todo。此分支失败时可能暂留已没有 Todo 的旧消息，日志必须记录已提交阶段与实际删除数量；后续新活动仍会阻止重试删除。

#### 页面缓存边界

已打开作品根本不会进入删除阶段，业务不会持有一边显示、一边被清理的数据。未打开作品的 active 指针和数据在维护层处理；下次打开时读取清理后的数据库。

本方案不调用页面的 `clearSession`，不遍历缓存 Provider，不取消消息保存计时器，不给发送或 Todo 写入增加清理分支。对作品持有状态的覆盖必须通过生命周期测试证明，不能把“不在当前屏幕”直接当成“没有缓存或后台使用者”。

### 5.4 调度、配置、日志与文案

保持后台周期清理，不在启动门等待清理完成。调度器每轮开始过滤保护作品，删除每棵树前再次核对。作品当前受保护时，本轮跳过即可，不在用户关闭作品时立即触发大批清理。

已打开作品的内容库变更历史和快照也跳过，避免同一维护过程仍在删除该作品的回滚依据；主库中其他独立历史表沿用自己的策略。后台运行仍须检查运行状态，不能由“作品未打开”推断 Agent 已经停止。

清理结果按 `normal_tree`、`orphan_tree`、`orphan_records` 输出候选、跳过、完成与失败组数量，以及实际删除的 session、message、Todo 和其他历史数量；另汇总 `unattributed`、跨作品冲突、循环和扫描失败数量。错误日志带作品 ID、根 ID 或缺失 session ID、阶段、表名和异常栈，不记录正文。

可识别的孤儿属于常规候选，不再逐条输出“无效关系”warning。仍需跳过的异常每轮汇总数量，逐条 ID 只在 debug 日志记录，避免相同残留每小时重复 warning；扫描或事务失败仍记录具体错误。

设置保持 `changeRecordRetentionDays`，默认 30 天，最小 7 天，最大 365 天。7 天是执行层的硬下限：设置读取、设置提交和清理服务构造及配置更新都要归一化到 7 至 365；历史配置中的 1 至 6 天按 7 天执行，不能只限制输入框。该范围已在基础实现落地。当前保留的设置文案为：

- 存储说明：设置历史记录保留时间，管理数据备份。
- 标题：历史记录保留时间。

标题下方的清理说明已按用户要求从组件和中英文翻译中移除，孤儿清理扩展不重新添加说明。桌面与移动端共用现有输入控件；备份仍指本地备份及用户配置的 WebDAV，不称为托管云端备份。

### 5.5 AskUser 提醒与超时自动处理

#### 等待期限

每次交互式 AskUser 最多等待 30 分钟。多个问题共用一次调用的期限，从待回答请求注册并发布问答卡片时开始计时；即使该 session 不可见，也立即开始计时。第 10 分钟提醒一次，第 30 分钟自动处理，两个时间点都相对同一个起点。编辑输入、切换页面、应用进入后台和通知权限请求均不重置期限。不新增用户设置项，不增加模型可调整期限的工具参数。

回答、主动取消和超时竞争同一个完成结果，只有最先发生的一项生效。完成后取消提醒和超时计时器，按本次运行及调用标识移除对应请求。超时后晚到的提交不能修改结果，旧回调也不能完成或移除复用同一调用 ID 的新请求；不能用清空所有等待请求代替按请求收尾。

计时不依赖清理调度器。移动端被系统挂起时，不能保证 Dart 定时器或通知准时执行。恢复后先检查原截止时间：已满 30 分钟则直接自动处理，不补发过期的 10 分钟提醒；已满 10 分钟但未满 30 分钟，且此前未提醒，则补发一次。提交入口也必须先检查截止时间，不能依靠定时器恰好先运行。

进程退出不恢复旧 Completer，不自动开启另一轮等待。重启后没有存活请求的历史问答显示为已中断并禁用提交，不能把进程退出记为超时。本轮不实现跨重启恢复执行。

#### 超时结果

30 分钟时不论 session 是否在前台，都按每道问题的推荐标记自动处理，然后把结果交还 Agent，继续当前回合：

- 有 `recommended=true` 的选项时自动选择推荐项。单选题只有一个推荐项时选它；多个选项被标为推荐时按原选项顺序选第一个。多选题选择全部推荐项，顺序与原选项一致。
- 没有推荐项的题目明确记为用户未回答。纯文本问题同样未回答，不猜答案，不把普通首选项当成推荐项。
- 多问题逐题处理，允许部分题目自动选择、部分未回答。自动选择沿用 `answers` 中的 `question_id` 和 `selected_options`；未回答题目的 ID 放入 `unanswered_question_ids`，不伪造回答文本。
- 自动处理统一返回 `ok=true`、`cancelled=false`、`resolution=timeout`，并提供 `answers` 与 `unanswered_question_ids`。这里 `ok` 表示工具已完成处理，不表示用户作出了回答。全部无推荐项时 `answers` 为空，并明确返回“用户未回答，请根据现有上下文继续”；不能只返回空答案让模型猜原因。
- 自动选择的结果和卡片都明确标为系统超时自动处理，不冒充用户亲自确认。不提交未发送的输入草稿或手动勾选草稿。工具描述说明自动选择的来源和未回答题目的含义，Agent 据此继续。
- 正常手动回答保留现有 answers 结构；主动取消保留 `user_cancelled`，不执行超时自动选择。

问答卡片进入 `timed_out` 终态，移除提交和取消操作。有推荐项时展示自动选中的答案及“等待已超时，已自动选择推荐项”；没有推荐项时显示“用户未回答，AI 将继续处理”；混合结果逐题显示自动选择或未回答。超时不是工具执行失败，也不取消当前 Agent，不自动重发原问题。

这只限制单次问答，不保证整个 Agent 任务在 30 分钟内结束，也不改变其他模型请求的超时设置。自动后台 headless 入口继续立即取消 AskUser，不引入人工等待或这套提醒计时。

#### 通知规则

复用现有 chat 的 `AiModeProcessingTracker` 和 `SystemNotificationService`。只有应用在前台且该 mode/session 已登记为前台可见时，才算用户正在查看会话；应用被最小化、隐藏或切到后台时，按未查看处理。通过 tracker 提供现有判断，不另维护一套 AskUser 前台状态。

| 时机 | 用户正在查看该会话 | 用户未查看该会话，或应用在后台 |
| --- | --- | --- |
| 问题出现 | 显示问答卡片，不发系统通知 | 立即发一次“AI 需要你的回答”通知，说明 30 分钟后自动处理 |
| 满 10 分钟且仍未完成 | 发一次“AI 仍在等待你的回答”通知，说明将在本次等待满 30 分钟时自动处理 | 同样发一次提醒 |
| 满 30 分钟且仍未完成 | 自动处理并更新卡片 | 同样自动处理并更新卡片 |
| 已回答、主动取消或运行中断 | 取消后续提醒与自动处理 | 取消后续提醒与自动处理 |

30 分钟不额外发送 AskUser 超时通知。Agent 后续完成时沿用原有 chat 完成通知。问题出现后的页面切换不新增即时通知，第 10 分钟的提醒覆盖仍未完成的请求。

同一提问的即时通知与 10 分钟提醒使用包含 mode、session、本次运行及调用标识的稳定标识，避免与其他会话、后续提问及 chat 完成通知相互覆盖。正文可包含作品标题，不包含问题正文、回答草稿或模型输入。

通知异步发送，不阻塞计时、回答或 Agent 收尾。权限申请或初始化完成后，真正发送前再次确认请求仍未完成且提醒阶段仍有效，避免已回答或已自动处理后才出现过时提醒。通知失败或权限被拒绝不影响 30 分钟自动处理；已显示通知的系统留存沿用现有 chat 行为。

点击通知只返回 Reveric，沿用现有 chat 入口，不新增跨端会话深链，不触发回答或模型调用。10 分钟提醒不受应用内前台过滤，但操作系统是否展示通知、移动端后台能否执行，沿用现有通知能力，不新增后台常驻服务或平台权限。

## 6. 验收标准

### 清理与配置

先在隔离测试库补回归，确认旧实现失败，再验证修复。禁止以用户业务库作为删除测试对象。

1. 保留时间最小 7 天；设置 1 至 6 天、读取旧配置和直接构造清理服务都不能绕过下限。已打开作品的全部会话和内容库历史保持不变；切到设置或应用后台后仍保护。
2. 同一作品有多个页面时，只有最后一个使用者退出才解除打开保护。
3. 作品页退出但父/子 Agent 仍运行时，仍然跳过。
4. 未打开且完整会话树或可归属孤儿组全部过期时，session、message、Todo 与命中的 active 指针按同一集合清理。
5. 任一子会话、消息或 Todo 有近期活动时，全树保留，旧消息不被截断。
6. 在候选扫描后打开作品，清理必须跳过；在清理提交期间打开作品，只在完整事务阶段结束后读取。
7. 订阅或 active 改动命中存活及缺失 ID 时均保护整组；循环、跨作品冲突、归属不明和缺失内容库按规则跳过。
8. 内容库失败不删除主记录；主库失败后可幂等重试；用户重新活动后不得继续使用旧候选。
9. 作品内容、记忆、用量、附件及其他作品指针不变。
10. 桌面与移动端打开/关闭边界、后台运行和窄屏设置文案分别验证。
11. 手动删除父 session 后，多个兄弟子树及缺失父 ID 的消息、Todo 合并为一个孤儿组；任一成员有近期活动则全组保留，全部过期后才回收。
12. 主记录物理缺失的消息、Todo 和 active 指针可按唯一作品归属回收；仅剩 Todo 无法归属时保留。软删除的主记录不得误判为不存在。
13. 缺失 ID 的订阅、active 变更或后台运行能保护孤儿组；来自其他作品内容库的同 ID 证据必须导致冲突跳过。
14. 候选扫描后主记录恢复、子树或归属发生变化、新消息或 Todo 写入时，旧候选不能删除；打开竞争分别覆盖孤儿树和无节点残留组。
15. 无节点残留组主库失败时消息不变；内容库失败时消息或指针仍能支持下轮归属与幂等重试；重试前的新活动仍受保护。正常树和有节点孤儿组继续验证内容库先提交的失败路径。
16. 内容库扫描不完整时不把未读库当空库；仅有 active 指针的残留按状态更新时间判定。重复清理不逐条输出相同异常的 warning，删除计数按三类分组核对。

### AskUser

1. 问题出现时，应用和 session 都在前台不通知；session 不可见或应用在后台时立即通知。
2. 满 10 分钟仍未完成时，无论前后台均提醒一次；切换页面、编辑输入和权限请求不重置时间，也不重复提醒。
3. 满 30 分钟，单选自动取推荐项、多选取全部推荐项、多个推荐标记按约定处理；无推荐、纯文本和多题混合分别返回正确答案及未回答 ID。
4. 自动结果明确标为 timeout，不提交草稿、不归为 user_cancelled 或工具失败；工具结果进入 Agent 后可继续当前回合。
5. 正常回答、主动取消和超时各自只完成一次，结束后无残留计时器或等待请求；边界时刻提交、晚到回调和同调用 ID 的后续请求互不干扰。
6. 会话取消及页面关闭沿用原有运行生命周期；仍在后台运行的请求继续计时，已中断的请求不再提醒或自动选择。
7. 通知失败不影响自动处理；权限异步返回后不发送已失效的通知；30 分钟不新增 AskUser 通知，chat 完成通知不受影响。
8. 挂起恢复时分别覆盖不足 10 分钟、10 至 30 分钟及已满 30 分钟，截止检查先于提交，已到期不补发提醒。
9. 自动选择、未回答和中断卡片在桌面及移动端正确展示；收尾保存后重读结果一致；重启后的失效历史卡片不可提交。
10. 自动后台 headless 入口仍立即取消，无新增提醒或等待。

## 7. 评测

被测对象是 AskUser 的结果契约和 Agent 后续行为，不评价正文质量，也不以模型是否喜欢某个推荐项判定功能正确。输入来自固定多题夹具和既有工具测试，时钟可控。

| 场景 | 期望 | 判定方式 |
| --- | --- | --- |
| 单选、多选、多个推荐标记 | 严格按 5.5 的规则选择，保留选项顺序 | 确定性测试 |
| 无推荐、纯文本、多题混合 | 未回答 ID 完整，不伪造文本，不提交草稿 | 确定性测试 |
| 超时结果送入 Agent | 识别为完成的工具结果，允许下一轮执行，不记为用户取消 | 使用可控模型响应的编排测试 |
| 用户未回答后实际续写 | 模型能区分自动选择与用户回答，按已有上下文继续 | 人工观察；不承诺非确定性文本完全一致 |

本次不运行真实 LLM E2E 评测；只有用户明确要求时再执行，不把手工观察当成已完成的自动化验收。

## 8. Token 成本

清理及通知不调用模型。AskUser 自动选择由确定性规则完成，不为选择答案新增模型调用；交还结果后继续正常 Agent 回合，因此相比无限等待可能产生后续模型费用，30 分钟不是整个任务的费用或时长上限。

工具描述增加固定契约文本；结果增加来源和未回答 ID，大小随本次问题及选中项数量增长，不附加作品全文。具体 token 增量本次未测量，不虚报数值；现有 Agent 的运行约束继续生效，本轮不新增模型档位或预算配置。

## 10. 已知妥协

1. 长期打开或运行中的作品会延迟清理。第一版优先保护在用数据；只有延迟清理造成明确空间问题时，再讨论更细的保护粒度。
2. 两个数据库没有原子事务。中断后可能暂留消息已清空的过期主记录；若重试和日志不足以满足恢复需求，再评估持久化清理任务。
3. 移动端挂起可能延迟 10 分钟提醒和 30 分钟自动处理。第一版复用现有通知能力，恢复后检查截止；只有需要后台准时执行时再单独评估平台能力。
4. AskUser 不跨重启续答，未完成内容也不保证已落库。第一版复用内存等待与现有保存流程；需要长期可恢复的后台执行时，再设计持久化执行状态及副作用恢复。
5. 点击通知只返回应用，已发通知留存沿用 chat 行为。需要直接定位待答会话或撤回已答通知时，再扩展通知导航与生命周期。
6. 可归属、全组过期的历史孤儿会被回收，但不恢复缺失父记录。仅剩 Todo 且无法归属、跨库冲突及循环暂留；手动删除继续可能产生新残留，由后续维护轮次检查。无节点残留组发生跨库失败时可能暂留已无 Todo 的消息，不承诺跨库原子性。
