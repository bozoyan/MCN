# 方案设计模板

> 用途：为 `docs/solutions/` 下的方案文档提供统一骨架。
>
> **分档使用。** 不要照抄全部章节。先判断方案规模，再决定写到哪一档：
>
> - **轻量档（默认）**：单模块改动、行为基本可预测。只写标有 `[核心]` 的节即可，背景/约束、目标、解决方案（决策）、改动清单、验收、任务管理。仓库里多数方案属于这一档（80 至 150 行）。
> - **完整档**：跨模块、含数据模型/migration、或涉及 AI 等非确定性输出时，按需追加标 `[按需]` 的节（ERD、任务依赖图、Migration、上线后验证、评测、成本）。
>
> 涉及用户行为或业务结果变化时，两档都必须写 5.7「业务监控与数据分析」；轻量档写清核心指标、统计口径、数据来源和查看时机即可。运营指标不自动扩展为采集系统建设或基础设施监控任务。
>
> 两档只区分方案规模。**每份交付方案都必须可执行**，不以「草案」或「后续确认」代替尚未完成的关键决策。可执行不等于已获准实施，实际改代码、迁移或发布仍按用户授权和项目规则执行。
>
> 标题中英不限，与同模块既有方案文档保持一致即可。

## 写作原则

1. **先说为什么，再说怎么做**：背景要解释真实问题，不能直接跳到实现。
2. **目标可验收**：目标必须能被测试、观察或人工确认；不要写「提升体验」「优化质量」这种无法闭环的表述。
3. **方案有取舍**：比较真正合理的备选方案，说明选择依据。没有实质备选时说明原因，不为填表编造一个明显更差的方案。
4. **实施可交接**：另一个工程师只读本文，应能知道改哪些模块、按什么顺序做、怎么验证。
5. **风险不藏起来**：无法第一版解决的问题放进「已知妥协」，不要伪装成已解决。
6. **交付前解决实施阻塞**：关键技术选型、公共契约、必需依赖和授权范围必须在方案交付前明确。尚有阻塞时如实报告未完成及需要解决的问题，继续核验或请求必要决策；不能仅列出负责人或改标「草案」，就把方案视为完成。最终方案不留 TBD、TODO 或「实现时再决定」。不影响当前交付的已确认范围取舍写入「已知妥协」。
7. **各节各司其职**：目标说明要达到的结果，实施说明怎么做，验收说明通过条件，评测检验 AI 等非确定性效果，上线后验证与业务监控观察实际运行。相同定义和指标只维护一处，其他章节引用，不重复堆叠同一段内容。

## 修订记录 `[按需]`

方案发生方向性变更时写，尤其是数据模型、migration 决策、兼容策略、范围增减、关键技术取舍发生调整时。新方案可省略本节。

**同一个聊天/会话内的迭代调整不写修订记录**，方案在对话中边讨论边改是正常起草过程，直接改正文即可。修订记录只用于方案归档后、跨会话发生的方向性变更。

```markdown
### YYYY-MM-DD

- 变更摘要：说明改了什么。
- 原因：说明为什么改。
- 决策：记录不适合放进方案本体、但后续维护者需要知道的上下文，例如开发期 migration 如何处理。
```

## 1. 背景 `[核心]`

说明这个方案为什么存在。

建议包含：

- 当前系统怎么工作。
- 触发问题的真实场景。
- 现有方案为什么不够。
- 问题影响范围：用户、数据、性能、维护成本、产品能力。
- 已知约束：历史兼容、平台差异、已有规则、不可改边界。

可选子节：

### 现状

用 3-5 条事实描述当前实现，不要评价。

事实以当前代码或实际操作为依据，标明关键文件、调用关系或验证记录；未运行的行为不能写成已验证。涉及已有方案或用户决策时，在背景中说明本次沿用、替代的内容及依据，有冲突先解决。不要把旧方案当成已经实现的现状，也不要把作者建议写成用户已确认的要求。

### 问题

按问题分组写清症状、根因、影响。

```text
问题：
- 症状：
- 根因：
- 影响：
```

### 约束

列出会影响方案选择的硬约束，例如：

- 不能破坏既有数据。
- 必须兼容旧会话 / 旧小说 / 旧配置。
- 必须使用现有工具链或平台能力。
- 不能引入新的运行时依赖。

## 2. 目标 `[核心]`

目标回答「做到什么算成功」。

### 目标

写可验证目标：

1. ...
2. ...
3. ...

### 非目标

明确本方案不解决什么，防止范围膨胀：

1. ...
2. ...
3. ...

### 成功信号

用可观察信号描述目标达成：

| 信号 | 验证方式 |
|------|----------|
| ... | 单测 / 集成测试 / 手动检查 / 数据观察 |

涉及产品效果的目标，在 5.7 中定义对应业务指标和判断依据。已有基线或明确目标时引用其来源；没有基线时先说明如何建立基线，不为填表编造目标值。

## 3. User Stories `[按需]`

当方案有明确的用户可见行为变化时写；纯内部重构 / 性能优化可省略。

从用户、开发者、系统维护者角度写。不要只写功能列表。

格式：

```text
作为 {角色}，
我希望 {能力 / 行为}，
以便 {价值 / 避免的问题}。
```

建议至少覆盖：

- 核心用户路径。
- 错误 / 失败 / 回滚路径。
- 旧数据或旧行为兼容路径。
- 开发者维护路径，如果方案引入新抽象或新数据模型。

示例：

1. 作为作者，我希望重新生成章节时能沿用最新故事状态，以便长篇连续性不依赖模型临场记忆。
2. 作为维护者，我希望能追踪某个结果来自哪次快照，以便排查质量回归。

## 4. 解决方案 `[核心]`

本节先说明合理选择及取舍，再给出明确决策。只有一种合理做法时说明依据即可，不强行填满方案对比表。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A | ... | ... | ... | 推荐 / 放弃 |
| B | ... | ... | ... | 推荐 / 放弃 |
| C | ... | ... | ... | 推荐 / 放弃 |

表格行数按实际选择保留。备选必须能满足基本目标，比较其真实代价与限制，不能用明显违反需求的做法充数。

### 决策

推荐方案：...

选择理由：

1. ...
2. ...
3. ...

拒绝方案：

- 方案 X：为什么不选。
- 方案 Y：为什么不选。

### 用户操作与信息归属

涉及用户可见流程时，说明用户从哪里进入、按什么顺序操作、得到什么结果，以及失败或取消后停在哪里。可以用一个贯穿样例或流程图表达，不用 User Stories 或功能列表代替实际操作流程。

涉及多个页面、视图或编辑入口时，还必须说明：

- 各视图分别负责什么，如何切换、定位，是否保留选择与编辑状态。
- 同一份内容由哪个业务对象保存，哪些入口可以修改，其他位置如何读取和展示。
- 修改如何影响其他视图、已有结果和下游操作，哪些变化自动生效、哪些需要用户明确应用。
- 用户正在编辑、尚未保存的内容与已保存数据如何区分；失败、取消或切换时如何处理。

| 内容 / 状态 | 保存该内容的业务对象 | 可编辑入口 | 其他视图如何使用 | 修改后的影响 |
|-------------|--------------------|------------|------------------|--------------|
| ... | ... | ... | ... | ... |

此处说明产品行为与信息归属；具体字段、关联和读写步骤分别在 5.1、5.3 展开，避免每个视图各存一份相同内容。

### 核心原则

列出实施时不能违背的原则，通常 3-5 条。

1. ...
2. ...
3. ...

### 关键假设

写出方案成立依赖的前提。

| 假设 | 如果不成立 | 应对 |
|------|------------|------|
| ... | ... | ... |

## 5. 方案实施

本节要让实现者知道「改什么、怎么改、按什么顺序改」。

### 5.1 模型设计 `[按需]`

如果涉及数据或领域对象，先定义模型。

```text
entity_name
- id
- field_a
- field_b
- status: active / archived
- created_at
- updated_at
```

说明：

- 字段语义。
- 唯一约束。
- 状态机。
- 生命周期。
- 是否冗余派生字段；如果冗余，为什么值得。

### 5.2 ERD `[按需]`

涉及多表或多对象关系时必须画。

```text
User
  |
  | 1:N
  v
Session ---- N:1 ---- Novel
  |
  | 1:N
  v
Message
```

说明每条关系的删除、归档、级联策略。

### 5.3 关键业务流程 `[核心]`

非平凡改动必写。用步骤或序列图说明最重要的流程，至少覆盖 happy path 和失败路径。

与第 4 节的用户操作对应，写清系统实际读取、校验、保存和返回什么；不重复描述按钮位置，也不能只有 UI → Service → DAO 的空泛分层。

```text
1. 用户触发 ...
2. 系统读取 ...
3. 系统校验 ...
4. 写入 ...
5. 返回 ...
```

复杂流程用图：

```text
UI -> Service -> DAO -> DB
 |       |        |     |
 |       |        |     +-- persist
 |       |        +-------- validate
 |       +---------------- orchestrate
 +------------------------ render state
```

### 5.4 改动清单 `[核心]`

**默认按文件分小节写**，每个文件下用要点列出「在哪个类 / 函数、加什么、为什么」。这是仓库里可交接性最高的写法，不要压成一行表格。

```markdown
#### `lib/.../foo_service.dart`
- `FooService.bar()`：新增 X 参数，原因 ...
- 新增字段 `baz`：用于 ...

#### NEW: `lib/.../foo_handoff.dart`
- `_trimContext()`：剥离 ...，保留 ...
```

涉及用户可见文案时，改动清单要包含 i18n 三件套（locale key + en/zh-CN 翻译），见 `.agents/rules/i18n.md`。

文件很多时，纯一句话能说清的改动也可用表格补充：

| 模块 / 文件 | 改动 | 原因 |
|-------------|------|------|
| `lib/...` | ... | ... |

文件数较多时**建议**按 PR / 任务拆分（见第 11 节），但不是硬性上限，内聚的一组改动可以放同一文档。

### 5.5 Migration `[按需]`

涉及 schema、配置、文件格式、历史数据时必须写。

Drift 表结构变更必须遵循 `.agents/rules/db-migration.md`：**schemaVersion + onUpgrade + Dart 模型类三者同步**。本节至少说明：

- schemaVersion 如何变化。
- 旧数据如何迁移。
- 默认值是什么。
- 回滚是否可能。
- 迁移失败如何处理。
- 是否需要一次性补数据脚本。

```text
from version N to N+1:
1. add column ...
2. backfill ...
3. create index ...
```

### 5.6 上线后验证 `[按需]`

本次改动存在需要在实际使用中确认的可靠性风险时写，比如生成任务恢复、文件保存或长时间运行。只覆盖受影响的功能与依赖；纯确定性改动可由第 6 节验收覆盖，不因方案属于完整档或使用 AI 就必须新增长期监控。

说明哪些现象需要关注、从哪里取得证据、出现问题后如何处理。优先使用已有业务记录和错误日志，不为填满本节新增指标系统。面向用户的失败提示遵循 `.agents/rules/error-handling.md`。

| 本次改动的风险 | 观察证据 | 异常判断依据 | 检查时机与处理 |
|----------------|----------|--------------|----------------|
| 例如，导出显示成功但文件损坏 | 实际输出文件、导出结果与错误日志 | 文件无法读取，或实际规格不符合导出合同 | 出现问题时复现对应输入，检查编码和交付步骤 |

业务使用情况与产品效果放在 5.7。上报队列积压、投递延迟、服务资源占用等系统指标，仅在本次方案实际修改对应机制或明确处理其可靠性问题时纳入；已有系统的日常维护不重复列入每个业务方案。

### 5.7 业务监控与数据分析 `[按需]`

涉及功能入口、核心操作流程、内容采纳、付费或其他用户行为与业务结果变化时必须写，轻量档同样适用。纯内部重构且不改变用户行为或业务结果时可省略。围绕第 2 节目标，说明发布后要回答什么产品问题、用什么数据判断，以及结果将影响什么决定。

#### 业务问题与指标

按实际目标选择少量指标，不要求每项都收集：

- 使用：多少人开始使用，是否再次使用。
- 流程：关键步骤到达情况、任务完成率和中断位置。
- 价值：结果是否被采纳、保存或继续使用，完成任务是否更省时。
- 可靠性与成本：生成或导出成功率、处理耗时、失败重试与实际消耗。
- 付费与留存：只有方案涉及对应业务目标时才纳入。

比如调整一个入口，可以观察点击、操作完成和失败；新增制作流程，可以观察开始制作、采用素材和导出成片。用户主动跳过可选步骤不等于流失，重做不一定是不满意，接口成功也不等于内容质量合格。

| 业务问题 / 对应目标 | 指标及统计口径 | 数据来源与查看方式 | 基线 / 判断依据 | 查看时机与后续行动 |
|---------------------|----------------|--------------------|-----------------|--------------------|
| ... | 分子、分母、去重单位、观察期及适用范围 | 已有事件、业务记录、查询或受控样本 | 已有基线、明确产品要求，或先建立基线 | 何时查看，结果将支持什么决定 |

指标口径写到能正确理解结果即可，不能只写“上线后观察”。不预设通用的完成率、失败率、延迟或样本量门槛；数值须来自已有数据、业务约束或明确确认的目标。没有历史数据时，先确定采样范围和比较方式；样本不足或观察期未结束时，记录暂不能判断。

#### 数据来源与必要的采集改动

先确认选定指标能否从现有业务记录、日志或分析入口取得。只有采用事件统计时，才需要说明对应事件、触发位置及关联方式；不要求所有方案都检查完整的客户端、后端和管理端链路。

优先使用本地业务记录、诊断日志和受控样本，不默认增加业务埋点。可选匿名诊断只有在构建配置了上报地址且用户同意后才启用；确需调整诊断协议时，核对 `AnonymousOutboxService` 和已接入服务的契约，不预设管理端看板或转化漏斗。

本次确需交付的采集或查询改动列入 5.4，并说明：

- 事件或记录的名称、触发时机、必要字段，以及如何关联同一次业务操作。
- 重试、重复调用、取消和失败如何计数，测试数据如何排除，平台和版本的统计范围。
- 对应改动的验证方式：新增事件检查触发与接收，修改聚合检查计数；只有改动投递、恢复或去重机制时，才验证这些机制的故障场景。
- 采集内容与必要范围，不默认上传正文、聊天内容或素材；匿名设备数不能直接当作账号用户数或跨设备留存。

数据暂不可得时写明缺口，不把缺失记成零，也不直接推导出新增后台报表或基础设施的任务。若该统计是已确认的交付要求，须给出必要实现与验收；否则将其与功能交付分开，说明当前能判断和不能判断的内容。

#### 发布后复盘

复用上表的查看方式、时机与行动，不另建重复的监控清单。对需要多人协作的事项再注明负责角色。

比较时保持统计口径、观察窗口和适用人群一致，按问题选择平台、版本、模型等分组。保留实际分子、分母、样本量与覆盖限制，写清继续观察或改进哪一步。前后变化只能说明相关性；需要判断因果时另行设计实验，不默认要求每个功能做实验。

## 6. 验收标准 `[核心]`

验收标准要覆盖功能、兼容、错误、性能或质量。

| 类别 | 标准 | 验证方式 |
|------|------|----------|
| 功能 | ... | ... |
| 兼容 | ... | ... |
| 错误处理 | ... | ... |
| 性能 | ... | ... |
| 可维护性 | ... | ... |

规则：

- 每条标准都要能判断 pass / fail。
- 不要写「体验更好」；写「某操作在 N 步内完成」「错误提示包含可操作原因」。
- 修改了哪些目录，就写对应测试命令（见 `.agents/rules/testing.md`）。
- 5.7 中明确属于本次交付的采集或查询改动，验证其触发、计数和结果；未改动的采集基础设施不作为功能验收前置。业务目标是否达成，按发布后的观察窗口复盘。

## 7. 评测 `[按需]`

当方案涉及 AI 行为、推荐、排序、生成质量、复杂状态机或非确定性输出时，必须写评测。

### 评测对象

- 被测能力：
- 不测内容：
- 输入来源：
- 输出判定：

### 评测场景

| 场景 | 输入 | 期望 | 判定方式 |
|------|------|------|----------|
| ... | ... | ... | deterministic / judge / manual |

### 自动化与人工评测边界

- 自动化能覆盖什么。
- 人工抽查什么。
- 哪些结果只作为观察，不作为阻断。

## 8. AI 与运行成本 `[按需]`

> 本节说明功能运行产生的 **AI 调用、计算、存储和传输消耗**，不是开发工时。只分析本方案实际改变的成本项。

涉及新增 prompt、增大上下文、增加模型调用次数、引入 subagent / 多轮编排、图片/音视频生成，或显著增加计算、存储、传输消耗时必写。

### 成本项与估算依据

| 成本项 | 计量 / 计费单位 | 单次用户任务的用量或计算式 | 依据与适用条件 | 放大因素与控制上限 |
|--------|-----------------|---------------------------|----------------|--------------------|
| 文本模型 | 输入 / 输出 token、调用次数 | 各次输入与输出之和，区分缓存计费 | 代表性输入估算或实测，注明模型和价格日期 | 上下文长度、多轮、重试、子任务 |
| 图片 / 音视频模型 | 张数、生成秒数、音频时长等实际计费单位 | 单次用量 × 尝试次数；不同规格分别计算 | 提供商计费规则、尺寸 / 时长与实测记录 | 批量规模、重生成、未采用结果 |
| 本地 / 服务端计算 | CPU / GPU 时间、内存峰值；计费时注明对应单位 | 预处理、渲染、编码等操作的用量 | 测试设备 / 服务规格及输入规模 | 并发数、分辨率、帧率、任务时长 |
| 存储与传输 | 字节、GB·月、上传 / 下载流量等实际单位 | 原始素材、结果、副本、备份与保留期限共同计算 | 文件样例、保留策略及服务价格 | 重复下载、缓存、副本数量、长期保留 |

删除不适用的行。分别标明用户向模型供应商付费、用户自配存储和用户设备承担的消耗；不能把这些成本混成一个没有口径的价格。

写清：

- 相比现状增加或减少哪些消耗，按一次完整用户任务计算，不只统计一次 API 调用。
- 失败、重试、重新生成和未采用结果如何计入；上游已完成后的重新下载不能当成重新生成计费。
- 是否随会话长度、小说篇幅、实体数量、媒体数量或时长放大；批量、并发、上下文和保留策略的上限是什么。
- 如何通过范围选择、模型档位、缓存、结果复用等控制成本；不能为了省成本静默截断业务内容或降低交付质量。
- 失败或超出预算时的明确行为，以及对离线使用和本地开发的影响。

没有实测时，给出计算方法、输入规模、假设和估算区间，标明「估算」，不能编造精确费用。若成本上限、关键规格或付费边界会改变技术选择或交付范围，须在方案交付前确认，不能作为实施后的开放问题。产品侧的实际采用成本与复盘口径引用 5.7，不重复维护一套指标。

## 9. 风险 `[核心]`

风险要写具体触发条件和应对。

| 风险 | 触发条件 | 影响 | 对策 |
|------|----------|------|------|
| ... | ... | ... | ... |

常见风险角度：

- 数据迁移失败。
- 旧行为兼容破坏。
- 并发 / 重入。
- 状态不同步。
- 性能退化。
- 工具或外部依赖失败。
- AI 输出不稳定。
- 用户误操作。

## 11. 任务管理 `[核心]`

每个方案只维护一张任务表，不另写任务详情。单文件方案放在正文末尾、本节所在位置；多文档方案放在总览 README 末尾，分篇只链接该表。附录检查清单可以放在任务表之后。方案正文保存需求、设计和验收标准，任务表保存执行进度。

| ID | 任务 | 状态 | 依赖 | 当前记录 |
|----|------|------|------|----------|
| T-01 | [可独立验收的交付结果](#6-验收标准-核心) | 待核对 | 无 | 核对当前入口、调用链和已有验收记录 |
| T-02 | [另一项交付结果](#6-验收标准-核心) | 待办 | T-01 | 已确认的具体缺口 |

- 一个任务对应一个可验收结果，包含实现及必要验证；任务名称链接正文中的需求与验收标准，不复制设计或另建详情。部分已实现、部分未实现时拆分任务，不写百分比。
- 状态统一为：**待核对**（尚未确认实际差距）、**待办**（已确认缺口）、**进行中**（正在实施）、**待验收**（实现已接通，必要验证未齐）、**完成**（完成条件及必要验收有证据）、**已取消**（明确不再执行）。缺少决策或外部条件时，在当前记录写明阻塞，不另增状态列。
- 未完成任务的当前记录写剩余工作或阻塞，必要时链接已核对的实现；完成后替换为交付结果、实现位置和验收证据，不保留剩余事项。若仍有任务范围内的工作，不能标完成；新增需求另建任务。取消时写原因或替代任务 ID。
- 证据只写实际核对或执行的内容：代码位置、提交、验证命令与结果、平台及日期。存在代码或测试文件不等于验收通过；未运行、跳过或未覆盖的平台必须明确，不重复要求已具备有效证据的验证。
- 表前注明核对日期、分支与提交，以及影响判断的未提交改动。代码或需求变化后，按影响更新相关行；不要将旧版本验证结果当作当前版本保证，也不要无依据重置其他任务状态。
- 开始执行前对照关联任务与当前代码；修改关联代码后、向用户报告前，同步更新该行。中断时留下具体停点，不能只写“进行中”。此前未关联方案的普通修改不要求扫描所有方案。
- 页首、导航表、依赖图和分篇不再重复写“已完成”“下一步”等进度。修订记录保存方向性决策，不充当第二份任务日志。

多任务依赖复杂时可以保留依赖图，但图中只写任务 ID、交付结果与依赖，不写状态。表中的依赖引用任务 ID；图与表都只表达实施顺序，不代表不同发布版本。
