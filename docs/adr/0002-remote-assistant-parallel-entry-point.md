# Remote Assistant as a parallel entry-point agent

We need a remote control feature letting users interact with Reveric from WeChat. The Chat Orchestrator is the existing primary agent behind the desktop chat entry point, bound to novel-scoped sessions (`AiChatSessions.novelId` is non-null) with workspace read+write tools. We decided to create a new **Remote Assistant** agent as the primary agent behind remote channel entry points (WeChat in V1), parallel to the Chat Orchestrator. The Remote Assistant is not a Chat Subagent and is not delegated to by the Chat Orchestrator — it is a separate entry-point agent with its own session model (cross-novel, persistent per remote user) and tool set (`list_novels` + `start_job` / `job_status` / `send_to_job` for background Jobs + `create_novel` / `edit_novel` / `list_chapters` / `share_chapter_review`). A **Job** is the primitive — a background writing execution started via `start_job` (implemented as a headless novel-scoped `AiChatSession`). A **Task** is a desktop todo (`todo` / `doing` / `closed`) executed by a **Task Run**; the Remote Assistant does not create Tasks. In V1 the Remote Assistant does not directly read or write novel workspaces — all workspace work is delegated to Jobs, to avoid the cross-novel `AiToolManager` refactoring. We chose this over extending the Chat Orchestrator to handle remote channels because the Orchestrator's novel-scoped session model and workspace-heavy tool set do not fit the cross-novel, routing-oriented remote use case.

## Consequences

- Remote Assistant and Chat Orchestrator are parallel entry-point agents, not a hierarchy. A user's desktop chat and WeChat chat are separate sessions with no shared state.
- Remote Assistant's tool set is maintained separately. Tools added to Chat Orchestrator do not automatically apply to Remote Assistant.
- The CONTEXT.md glossary gains a new agent category (entry-point agents), with Remote Assistant as the first non-Orchestrator example. Job and Task are distinct glossary terms.
- Remote Assistant conversations persist in dedicated app-DB tables (see ADR-0006, which supersedes the virtual `novelId` approach of ADR-0004).
